PADEL ARENA WEBSITE — FULL IMPLEMENTATION SPECIFICATION
FOR CODEX / DEVELOPER IMPLEMENTATION

====================================================================
1. DOCUMENT PURPOSE
====================================================================

This document defines the required pages, behaviors, system logic, API
structure, database structure, user flows, validation rules, and admin
workflows for the Padel Arena website.

This specification is intended to be detailed enough for Codex or a
developer to implement the platform without needing additional planning.

Selected pages to implement in this phase:

1. Home
2. About Us
3. Courts / Facilities
4. Booking
5. Pricing
8. Tournaments / Events
10. Contact Us
11. FAQ
12. User Account / My Bookings
13. Admin Dashboard

The website must serve two main business goals:

1. Present the padel arena as a professional and premium sports venue.
2. Let users discover information and complete online court bookings.

====================================================================
2. PRODUCT GOALS
====================================================================

Primary goal:
- Increase completed court bookings.

Secondary goals:
- Increase direct customer inquiries.
- Display pricing clearly.
- Promote events and tournaments.
- Reduce manual booking via phone or WhatsApp.
- Give staff a simple dashboard to manage operations.

Success criteria:
- A guest can visit the site and understand the venue within seconds.
- A user can complete a booking with minimal friction.
- An admin can manage courts, pricing, bookings, events, and inquiries.
- The website works well on desktop and mobile devices.

====================================================================
3. USER TYPES
====================================================================

3.1 Guest Visitor
Can:
- View all public pages
- Browse courts and prices
- View tournaments/events
- Submit contact form
- Start booking flow
- Continue as guest checkout if enabled

Cannot:
- View personal bookings
- Manage bookings after placement unless connected by email link flow
- Access admin dashboard

3.2 Registered Customer
Can:
- Register and log in
- Create bookings
- View upcoming bookings
- View booking history
- Cancel or reschedule within policy rules
- Update profile details

3.3 Admin
Can:
- Access admin dashboard
- Manage courts
- Manage operating hours
- Manage pricing rules
- Create, edit, delete events
- View and manage all bookings
- Block maintenance times
- View contact form submissions
- Manage FAQ entries
- Manage homepage banners/content if implemented as editable content

9. DATABASE RELATIONSHIPS
====================================================================

- users (1) -> (many) bookings
- courts (1) -> (many) bookings
- courts (1) -> (many) blocked_slots
- courts (1) -> (many) pricing_rules
- admin users (1) -> (many) blocked_slots via created_by_admin_id

Rules:
- booking cannot overlap existing confirmed booking for the same court/date
- booking cannot overlap active hold for same court/date
- booking cannot overlap blocked slot
- pricing rule chosen must be deterministic using priority logic

11. BOOKING SYSTEM ALGORITHM
====================================================================

This logic is critical.

11.1 Availability Calculation
Inputs:
- requested date
- requested duration
- optional court filters
- optional preferred start time

Algorithm:
1. Validate date is not in the past.
2. Load arena operating hours for selected day.
3. Load active courts.
4. Filter courts by selected options.
5. Generate possible time slots within opening hours.
6. Remove slots overlapping:
   - confirmed bookings
   - pending holds that have not expired
   - blocked maintenance slots
7. Return valid slots by court.
8. Optionally compute price per slot in response.

11.2 Hold Creation
When user selects a slot:
1. Re-check availability server-side.
2. Create temporary hold with expiry time.
3. Return hold details and price summary.
4. Frontend starts countdown timer.

11.3 Final Booking Creation
1. User submits booking against hold_id.
2. Server verifies hold exists and is not expired.
3. Server verifies slot is still valid.
4. If payment is required now:
   - process payment or mark pending external payment
5. Create booking record.
6. Delete or invalidate hold.
7. Send confirmation.
8. Return booking reference.

11.4 Cancellation Logic
Rules configurable by setting:
- cancellation allowed only if booking start is more than X hours away
- otherwise block cancellation or require admin action

11.5 Reschedule Logic
1. Check user/admin permission.
2. Check booking is eligible for reschedule.
3. Check new slot availability.
4. Update booking details.
5. Save audit note if needed.
6. Notify user.

====================================================================
13. BUSINESS RULES
====================================================================

- One court cannot have overlapping bookings.
- Inactive courts must not appear in public booking search.
- Maintenance-blocked courts must not allow new bookings in blocked period.
- If guest checkout is enabled, guest bookings must still store name/email/phone.
- Booking reference must be unique and human-readable.
- Completed and cancelled bookings remain in history.
- Public pages must only show published/active content.
- Upcoming events are event_date >= today and status = upcoming.

- Saves as upcoming
- Event appears on Events page and possibly homepage preview

- Admin adds new FAQ item

- Item appears on public FAQ page in correct order
